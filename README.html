The experiment loop

One card per experiment: experiments/<ID>/card.md. State lives in files (registry.json, cards, NOTEBOOK.md), not in chat.

  1. Classify the task: infrastructure (spec + tests), experiment (this loop) or analysis (a cited report).
  2. Draft the card. It has one change under test, a baseline, and metrics and gates declared before launch.
  3. ⛔ You approve the card on its review page. No config, launcher or run before this.
  4. Config, launcher, and a smoke test that passes locally.
  5. Launch: the agent runs cheap local jobs and hands cluster jobs to you, then waits. No numbers are invented.
  6. Analyze real outputs. The skeptic tries to refute the result.
  7. ⛔ You confirm the verdict. The agent proposes; it never declares a gate passed.
  8. The notebook entry and the registry row are updated.

Review cards in the browser

Markdown in, one interactive page out. No Node or Python needed.

  1. Render: sh scripts/render.sh experiments/<ID>/card.md (Windows: scripts/render.ps1). It writes card.html next to the card.
  2. Open the page. The overview shows at a glance, the status, the ⛔ gate box and needs your decision. Sections collapse, and the page has light and dark themes.
  3. For each item: Accept, Change, Reject, Answer or Comment. Then Approve card, or later Confirm verdict.
  4. Save card.feedback.md (or copy it) and tell the agent “read the feedback”. It updates the markdown and re-renders the page.

Install in one prompt

  1. Copy this kit into your project root: my-research/research-onboarding-kit/.
  2. Open your coding agent in my-research/ and run:
Read `research-onboarding-kit/instructions.md` and configure this repository to use Research Driven Development with this harness. Ask me all necessary questions before making project-specific decisions.

The agent confirms your harness, inspects the repository and asks the questions in questions.md. It then generates the harness and proposes a first card, usually a baseline reproduction.

Short on time? Accept the recommended defaults in one answer. Only the project-specific questions remain: domain, commands and compute, data and frozen artifacts, the evaluation gate and the smoke test.

Human-gated by design

  • Two gates the agent never crosses. It does not approve cards or confirm verdicts, and it never writes an approving feedback file itself.
  • No expensive compute without approval. A smoke test passes before any cluster job.
  • Frozen artifacts never change. A replacement gets a new name and a decision.
  • Every run is logged. No silent retries, no metric shopping.
  • No secrets in memory. Lessons and decisions are proposed, and nothing is written without approval.
  • Nothing phones home. Hooks and MCPs are off by default; autonomy is read-only monitoring.

Stay current, contribute

Updates

Watch the repository's releases on GitHub. In an installed project, invoke the rdd-update skill. It refreshes kit files, merges your adaptations with your approval, and runs the migration notes from CHANGELOG.md.

Contributing

Fork, branch from main, one concern per PR. Keep render.sh and render.ps1 in sync, re-render the examples, keep the hook adapter identical and installable files harness-neutral.
