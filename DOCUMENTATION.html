Research Onboarding Kit

How to install a Research Driven Development harness and use it day to day. For an overview, see the landing page.

1What is RDD

Research Driven Development applies the spec-first discipline of the SDD kit to research. The central object is the experiment card, not a feature spec. A card tests one hypothesis with exactly one change against a baseline, with metrics and gates declared before launch.

Two human gates sit where research goes expensively or dishonestly wrong: ⛔ approving the card, before any compute is spent, and ⛔ confirming the verdict, before any claim is made. Everything else stays friction-free: reading, plotting, drafting and infrastructure work.

Failure modeCountermeasure
Simultaneous changesOne change per card (C1)
Mutated or leaked eval dataFrozen manifest + check_frozen.py
Silent retries, cherry-pickingEvery run in the card's Runs table
Wasted computeSmoke test before any cluster job
Untraceable claimsEvery number cites a card or dataset ID

2Installation

Copy the kit into the project root, open your coding agent there, and run:

Read `research-onboarding-kit/instructions.md` and configure this repository to use Research Driven Development with this harness. Ask me all necessary questions before making project-specific decisions.

The agent works in six phases:

  1. Inspect: stack, compute, tracker, data, prior baselines, existing harness directories.
  2. Ask: the questions in questions.md, starting with the defaults profile (§0 is the harness).
  3. Generate: AGENTS.md, project map, skills, render assets and renderer, PLAN.md, registry, notebook, decisions, roles, approved hooks, validators, .gitignore entries, the first render, and finally the manifest.
  4. Validate: validate_structure.py, validate_registry.py, check_placeholders.py, and pages that open styled.
  5. Summarize.
  6. Propose a first card: usually a baseline reproduction, rendered and waiting for approval.
With the recommended defaults profile, only the project-specific questions remain: domain, commands and compute, data and frozen artifacts, the evaluation gate and the smoke test.

4Daily workflow

1 · Draft a card

Use the research-workflow skill: I want to test <one change> against <baseline>. Draft the card, render it, and stop — no configs or launches until I approve it on the page.

The agent classifies the task and writes experiments/<ID>/card.md. It adds a draft registry record, renders card.html and stops.

2 · ⛔ Approve in the browser

Open card.html. The gate box shows the hypothesis, the one change and the gates. Review each item, click Approve card or Request changes, save card.feedback.md, and say “read the feedback”.

3 · Smoke test, launch, wait

The agent builds the config, the launcher and the smoke test, and runs the smoke test locally. It then runs the job if it is cheap and local; otherwise it hands you the exact command. It logs every run and never fills in expected numbers.

4 · ⛔ Confirm the verdict

When results land, the agent checks them against the gates and runs the skeptic. It then fills in Results and proposes a verdict (analyzed). On the page, click Confirm verdict or Dispute verdict. Confirmation sets done; the scribe updates the notebook and registry.

Lost in a long answer? Use the bro skill. Stopping for the day? Use closing.

A rerun of the same axis gets a new card (__v2, supersedes:). After approval, the design sections are append-only.

6Documents and review page

Every human-facing document is markdown with frontmatter (doc: names its type). The agent reads and writes only the .md; the page is rendered from it and never edited.

doc:File
cardexperiments/<ID>/card.md: the whole experiment in one file
planPLAN.md: objectives, phases and gates, experiment matrix
notebooknotebook/NOTEBOOK.md: newest first, ## Resume here on top
analysisreports/<slug>.md or experiments/<ID>/analysis.md
infra-specspecs/<module>/spec.md: contract, requirements, acceptance tests
docAny other note, design or proposal

Card sections

The card's sections, in order:

  • Summary
  • Hypothesis H1
  • Change under test C1
  • Baseline
  • Metrics and gate M1/G1
  • Setup
  • Open questions Q1 and Assumptions A1 (both optional)
  • Plan (timeline T1)
  • Runs
  • Results
  • Skeptic BLK-1/NBK-1
  • Verdict
  • Follow-ups

Render

sh scripts/render.sh experiments/E012_frozen-encoder/card.md   # → card.html
sh scripts/render.sh experiments/                              # registry.html + docs in the folder
sh scripts/render.sh --all                                     # everything (from the project root)
pwsh scripts/render.ps1 …                                      # Windows

Each page opens on an overview with these parts:

  • At a glance
  • the status stepper
  • key stats
  • a ⛔ gate box when a decision is due
  • Needs your decision

Collapsible sections follow, with a section nav. ID chips link to their definitions, and the page prints cleanly. No runtime is needed: the markdown is embedded and rendered in the browser.

Feedback

Items with an ID get Accept / Change / Reject / Answer / Comment buttons. The page verdict follows the decision that is due:

  • a draft card shows Approve card (gate 1)
  • an analyzed card shows Confirm verdict (gate 2)
  • a pending plan shows Approve plan

The researcher saves <name>.feedback.md next to the source, downloads it, or copies it into the chat. The agent applies it to the markdown, re-renders, deletes the file and summarizes in ≤ 5 lines. An approving file with no change or reject items is the gate decision, but only if the feedback did not also change the document. The agent never writes an approving file itself.

Conciseness budgets

Summary≤ 3 sentences (shown as “At a glance”)
Item, card field, findingOne sentence
SectionOne screen, or a table
Card plan≤ ~8 steps; a card reads in about three minutes

Each fact lives once and is referenced by ID elsewhere; optional sections that do not apply are deleted. Full conventions are in skills/research-workflow/doc-format.md.

7The registry

experiments/registry.json is the machine source of truth for status. Each card's frontmatter mirrors its status and gate_result. validate_registry.py checks that records, card frontmatter and results/<ID>/ agree; on disagreement, artifacts win. registry.html is a rendered dashboard: it shows counts by status and gate result, status filters, and links to each card. See the example.

The registry complements an existing tracker (W&B, MLflow, TensorBoard); it never replaces one.

10Hooks

The hooks are example scripts and are disabled by default. Every script starts with the same adapter block, which reads Claude Code, Codex, Cursor and Antigravity payloads, or RDD_HOOK_FILE, RDD_HOOK_COMMAND and the other RDD_* variables. Output follows RDD_HOOK_OUTPUT (exit, cursor, antigravity, plain). The scripts fail open without jq.

HookClassEffect
suggest-card.shAdvisoryConfig/launcher work without an approved card
frozen-path-warning.shAdvisoryWrite to a frozen path
smoke-test-reminder.shAdvisoryLauncher written before smoke_passed
post-results-reminder.shAdvisoryResults arrived: fill Runs/Results, skeptic, re-render
block-unapproved-launch.shBlocking (opt-in)Configs/launchers before gate 1
block-frozen-writes.shBlocking (opt-in)Writes to frozen artifacts

Gate 2, verdict confirmation, has no hook substitute by design. Wiring for each harness is in hooks/settings-snippets.md, and the hook contract is in hooks/hooks-policy.md.

11MCPs and CLIs

The kit is local-first: no MCP and no external CLI is required. Paper-search or tracker MCPs are added only on opt-in, following mcps/mcp-criteria.md. Prefer a single permission-gated CLI call for one-off reads and a scoped MCP for repeated access. Any remote mutation needs per-action approval (reference/cli-vs-mcp-policy.md).

12Policies

Research integrityGates declared before launch; every run logged; no metric shopping; changing a gate needs a dated decision
ReproducibilityConfig-as-spec, seeds, environment capture, code SHA, data hashes
Compute budgetSmoke test first; expensive, cluster or paid runs are handed to the researcher
Frozen artifactsNever mutate; manifest + checksums; replacements get new names
Human in the loopTwo gates; a gate decision can arrive as a feedback file, never one the agent wrote
MemoryProject memory first; global memory only with approval of the exact text; no secrets
AutonomyRead-only monitoring with stop conditions; never launches expensive jobs or crosses a gate. One recorded exception: the opt-in goblin-mode pack, scoped to a single invoked card
Session recoveryRead ## Resume here, then reconcile registry and cards against results/; artifacts win
Dependency freshnessCheck current docs before changing ML frameworks and APIs; evidence in the card's Setup
Context economyShort AGENTS.md; procedures in skills; durable truth in files

Each policy lives in reference/.

13Updating

Onboarding writes <harness-dir>/rdd-kit-manifest.json with the kit version, the harness block (primary and additional directories), and one record per installed file: kit path, hashes and an adapted flag. Invoke rdd-update in the project to update the harness. It:

  • fetches the kit
  • refreshes unmodified verbatim files mechanically
  • merges adapted files with approval
  • runs each CHANGELOG.md migration step with approval
  • rewrites the manifest

1.x installs have no manifest, so rdd-update runs in bootstrap mode and converts the HTML cards to markdown. Watch the GitHub releases to hear about new versions.

16Prompts

Read the feedback for <ID>, apply it to the card, re-render, and tell me in 5 lines what changed.
The card for <ID> is approved. Build the config, launcher and smoke test; run the smoke test locally. Give me the exact cluster command — don't submit it.
Results for <ID> are in results/<ID>/. Verify against the gates, run the skeptic, fill Results, propose a verdict and render the card for me to confirm.
I've been away. Reconcile the registry and cards against results/ — artifacts win.
Use the closing skill before I stop.

More prompts are in usage-prompts.md.
